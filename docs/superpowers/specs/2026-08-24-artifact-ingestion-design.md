# Content-Addressed Artifact Ingestion Design

## Goal

Introduce the deterministic boundary between source adapters and later verification/release materialization.

The ingestion layer converts byte-bearing adapter discoveries into exact-byte artifact facts backed by a local content-addressed object store. It preserves source provenance without trusting source-declared metrics as computed facts, performs only SHA-256 exact-byte deduplication, and does not invoke the verifier, normalizer, or release builder.

This is the first downstream layer after source adapters. It is deliberately smaller than a full importer.

## Context

The repository already has two distinct ends of the pipeline:

- source adapters acquire pinned source snapshots and discover source-specific puzzle, solution, and semantic facts;
- `release.py` consumes four schema-valid generated JSONL configs and builds reproducible release artifacts.

The missing boundary is deterministic materialization of exact puzzle/solution bytes into canonical artifact identities.

The dataset specification defines exact bytes as the v1 deduplication boundary and keeps source observations, verification, normalization, and release projections as separate concepts. The release `solution` schema currently requires verifier fields, so artifact ingestion must not manufacture placeholder verifier revisions, validation profiles, or computed metrics merely to fit the release schema.

## Decision

Add one focused module, `src/opus_corpus/ingestion.py`, containing the byte-ingestion data model and deterministic materialization functions.

Do not make `release.py` source-aware. Do not add adapter-specific conditionals to ingestion. Orchestration will translate adapter outputs into a generic byte-bearing candidate type, and ingestion will operate only on that generic contract.

The module owns:

1. exact byte reading and hashing;
2. content-addressed local object publication;
3. deterministic artifact IDs;
4. exact-byte deduplication;
5. fail-closed conflict detection;
6. conservative artifact-level rights aggregation;
7. retention of source provenance and source-claimed metrics as observation inputs.

It does not own source acquisition, verification, normalization, source-semantic parsing, frontier logic, or release JSONL generation.

## Input contract

`ObservedArtifactCandidate` represents one source assertion about one byte-bearing artifact.

Required fields:

- `artifact_kind`: `puzzle` or `solution`;
- `puzzle_id`: repository-defined canonical conceptual puzzle ID;
- `path`: local filesystem path containing the exact observed bytes;
- `artifact_format`: source artifact format such as `puzzle` or `solution`;
- `rights_status`: `redistributable`, `local_fetch_only`, or `unknown`;
- `source_id`: stable source adapter ID.

Optional provenance fields:

- `source_revision`;
- `source_object_id`;
- `source_path`: stable upstream-relative path/object key, never the local cache root;
- `source_url`;
- `author`;
- `retrieved_at`;
- `claimed_cost`;
- `claimed_cycles`;
- `claimed_area`;
- `claimed_instructions`.

`retrieved_at` is not generated by ingestion. It may be absent until acquisition records a stable retrieval event. A later observation materializer must require a stable timestamp before emitting the current `observation.schema.json` projection. Build-clock time must never be substituted because that would make repeated offline builds logically different.

Source-declared metrics remain provenance facts. They are never copied into computed solution fields by ingestion.

## Output contract

The ingestion result contains two logically separate products.

### Artifact facts

`ArtifactRecord` contains:

- `artifact_kind`;
- `artifact_id`;
- `puzzle_id`;
- `sha256`;
- `byte_length`;
- `artifact_format`;
- aggregate `rights_status`;
- content-store relative object key.

The record contains no local absolute path, retrieval timestamp, source-specific path, claimed metric, verifier field, or normalized representation.

### Provenance inputs

`ArtifactProvenance` retains each distinct source assertion associated with an artifact:

- `artifact_id`;
- `puzzle_id`;
- source identity/revision/object/path/URL;
- author;
- optional stable retrieval timestamp;
- source-declared metrics;
- source-level rights status.

This is an internal typed fact, not yet a release `Observation` row. Observation IDs and schema projection belong to the later materialization layer.

## Artifact identity

Artifact IDs are deterministic functions of artifact namespace and SHA-256:

- puzzle artifact: `om.puzzle-artifact.sha256.<64-hex-digest>`;
- solution artifact: `om.solution.sha256.<64-hex-digest>`.

The SHA-256 digest is over the exact source bytes with no parsing, newline normalization, decompression, reserialization, or semantic canonicalization.

The namespace prefix keeps puzzle and solution identities distinct even if the same byte string is ever observed in both roles. Physical object storage may still share the single digest-addressed blob.

No counters, mutable registries, timestamps, source names, file names, or collection IDs participate in artifact identity.

## Content-addressed object store

Ingestion publishes exact bytes into a caller-provided artifact object root using a SHA-256 layout such as:

`sha256/<first-two-hex>/<64-hex-digest>`

The object path contains no source name or original filename. Source layout remains provenance, not storage identity.

Publication uses one read of the source payload:

1. open the candidate file once;
2. stream its bytes into a temporary file located on the destination filesystem while computing SHA-256 and byte length from the same stream;
3. derive the final digest object path only after that stream is complete;
4. if the digest object already exists, verify that the existing object hashes to the expected digest and discard the temporary copy;
5. otherwise atomically publish the temporary file at the digest object path;
6. never overwrite a mismatching existing object silently.

Hashing and stored bytes therefore describe the same byte stream. Ingestion never hashes one read and then reopens the source to obtain the payload that is stored.

The store is a canonical exact-byte cache downstream of source snapshot acquisition. It does not replace adapter caches: adapter caches preserve pinned upstream snapshots, while the object store deduplicates exact byte artifacts across those sources.

## Deduplication and conflicts

V1 deduplication is exact-byte only.

Candidates with the same `artifact_kind`, `puzzle_id`, SHA-256, and compatible format converge onto one `ArtifactRecord` and retain multiple provenance inputs.

Candidates with different hashes always remain different artifacts, even when they have the same filename, score, author, normalized structure, or apparent machine behavior.

Fail closed on ambiguous identity:

- the same solution digest associated with different canonical `puzzle_id` values;
- the same puzzle-artifact digest associated with different canonical `puzzle_id` values;
- the same kind/puzzle/digest described with conflicting artifact formats;
- a missing, unreadable, or non-file source payload;
- a corrupt pre-existing object-store blob whose contents do not match its digest path.

The same physical digest may exist in puzzle and solution namespaces without conflict because the semantic entity kinds are intentionally distinct.

## Rights aggregation

Each provenance input retains its source-level `rights_status` unchanged.

The artifact-level status is a deterministic conservative fold over all observations of the exact artifact:

1. if any provenance says `local_fetch_only`, artifact status is `local_fetch_only`;
2. otherwise, if any provenance says `unknown`, artifact status is `unknown`;
3. otherwise artifact status is `redistributable`.

This aggregation is publication-safety policy, not a claim that all sources agree about licensing. Source-level statuses remain available for later auditing.

Raw bytes are stored locally regardless of publication status because verification requires exact payloads. Publication/export policy continues to decide whether those bytes may leave the local build environment.

## Provenance deduplication

Artifact deduplication must not erase source evidence.

Two provenance inputs are considered the same source assertion only when all provenance fields are identical. Exact duplicate inputs may collapse deterministically; inputs from different sources, revisions, upstream paths, authors, retrieval events, rights statuses, or claimed metrics remain separate.

Provenance ordering in returned results is deterministic and independent of local filesystem roots. Sorting uses stable source/provenance fields, never the candidate's local `path`.

## Adapter integration

The ingestion module does not import concrete adapters.

A later orchestration layer will wrap current adapter outputs as candidates, for example:

- `OmsimAdapter.puzzle_path(...)` -> puzzle candidate;
- `OmArchiveAdapter.solution_paths(...)` -> solution candidates;
- `OmLeaderboardAdapter.solution_candidates(...)` -> solution candidates carrying source-claimed metrics.

`MoleculeDbAdapter` semantic output is not an exact official puzzle byte artifact and therefore does not enter this byte-ingestion path. Its molecule semantics remain independent source evidence for later normalized-puzzle derivation.

`LeaderboardBotAdapter` identity facts likewise remain identity/reconciliation evidence rather than byte artifacts.

## Release integration

This slice does not write `puzzles.jsonl`, `solutions.jsonl`, `observations.jsonl`, or `normalized.jsonl`.

That separation is intentional:

- puzzle release rows need a policy for selecting a canonical puzzle artifact when multiple exact artifacts exist;
- solution release rows currently require verifier-derived fields and therefore should be created only after real verification;
- observation rows require stable observation IDs and a stable retrieval timestamp;
- normalized rows require a versioned normalizer.

The later materialization layer will project artifact facts, provenance, verification results, and normalized records into the existing release inputs. Existing `release.py` remains a deterministic validator/builder over those generated inputs.

The ingestion model includes `byte_length` even though the current release puzzle/solution schemas do not expose it. The dataset specification requires byte length at the artifact layer; release schema evolution or projection policy can be addressed when materialization is implemented rather than dropping the fact during ingestion.

## Verification handoff

The verifier layer consumes:

- one ingested puzzle artifact record plus its object-store blob;
- one ingested solution artifact record plus its object-store blob;
- a pinned verifier revision and validation profile.

Verification produces new derived facts. It must not mutate artifact identity or provenance.

A failed verification leaves the ingested source artifact intact and available for provenance, debugging, and future verifier revisions.

## Determinism

Given the same candidate bytes and stable provenance fields, ingestion must produce identical logical artifact/provenance records regardless of:

- source-cache root location;
- artifact-object root location;
- candidate iteration order;
- operating directory;
- wall-clock build time.

Local absolute paths may be used to read bytes but must not enter IDs, hashes, canonical records, sort keys, or exported provenance.

## Error model

Introduce a typed ingestion exception such as `ArtifactIngestionError` for deterministic input/store failures.

Error messages should identify the artifact kind, canonical puzzle ID, and stable source provenance where available, without making local absolute paths part of canonical output.

The operation is fail closed: conflicting identities or corrupt content-store state are surfaced rather than repaired heuristically.

## Testing

Tests use synthetic local byte files and fixed provenance data. No network access or real upstream repositories are required.

Required cases:

1. stable SHA-256, byte length, object key, and deterministic puzzle/solution IDs;
2. identical solution bytes from two sources produce one artifact plus two provenance inputs;
3. identical puzzle bytes from two sources produce one puzzle artifact plus two provenance inputs;
4. different byte strings never deduplicate;
5. identical physical bytes in puzzle and solution namespaces yield distinct artifact IDs while sharing the digest object;
6. the same solution digest attached to different puzzle IDs fails closed;
7. conflicting format declarations for one semantic artifact fail closed;
8. conservative rights aggregation is deterministic while source-level rights remain unchanged;
9. source-claimed metrics remain provenance-only;
10. missing/non-file/unreadable inputs fail explicitly;
11. a corrupt existing object-store blob fails rather than being overwritten;
12. candidate order does not affect returned logical records;
13. moving both source files and object store to different local roots does not change logical records;
14. exact duplicate provenance assertions collapse while distinct assertions remain separate;
15. the stored object hash and byte length are computed from the same single source-file read.

## Non-goals

This slice does not implement:

- source fetching or repository snapshot caching;
- canonical puzzle-artifact selection policy;
- puzzle parsing;
- solution parsing;
- verifier execution;
- computed metrics;
- validation-profile semantics;
- normalizers;
- observation schema projection or observation IDs;
- release JSONL generation;
- release schema changes;
- Pareto/frontier derivation;
- Hugging Face export changes;
- semantic-equivalence deduplication.

## Acceptance criteria

The slice is complete when:

1. byte-bearing adapter discoveries can be wrapped in a source-agnostic candidate contract;
2. exact bytes are materialized into a deterministic SHA-256 object store;
3. artifact IDs are stable and content-derived;
4. exact-byte duplicates converge without losing provenance;
5. conflicts fail closed rather than being resolved heuristically;
6. source claims remain observation inputs rather than computed facts;
7. no verifier or release placeholder facts are invented;
8. tests demonstrate directory-, order-, and clock-independent logical output;
9. existing adapter and release behavior remains unchanged.
