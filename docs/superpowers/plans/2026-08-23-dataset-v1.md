# Opus Magnum dataset v1 implementation plan

Date: 2026-08-23
Status: approved for execution
Branch: `feat/dataset-v1`

## Goal

Produce a reproducible, immediately usable Opus Magnum base-game solution dataset for the frozen `base-game-2026-06-16` collection. The repository must be able to validate its collection contract, acquire pinned public source material, index executable solutions with provenance, verify solutions with a pinned `omsim/libverify`, and export a loading-script-free Hugging Face dataset as deterministic Parquet plus a dataset card.

The public/default export is metadata-only for source payload classes whose redistribution rights are unresolved. It still contains stable raw-source URLs, hashes, scores, provenance, and verification results so consumers can hydrate executable artifacts from their original source. A local full build may retain puzzle and solution bytes in the content-addressed cache but must not publish them by default.

## Pinned upstream inputs

- Collection membership: `F43nd1r/zachtronics-leaderboard-bot@ca40dee95da584270eb3be1c4b74e2be63afa7e6`.
- Leaderboard solution repository: `F43nd1r/om-leaderboard@c8fbd45dd05a479486606c352570d877c8986347`.
- Verification implementation: `ianh/omsim@758f4a4b4c9e24f50294801da774a0960c922bab`.
- Puzzle acquisition endpoint: Zachtronics Leaderboard `/om/puzzle/{leaderboard_key}/file`; every acquired puzzle is hashed immediately and the expected hash inventory is frozen once generated. Subsequent builds reject byte drift.

The leaderboard application exposes both built-in puzzle bytes and record solution files; its backend repository stores paired `.json` score metadata and `.solution` artifacts. `omsim` includes `test-against-leaderboard.py`, which compares leaderboard metadata to `libverify` measurements and therefore establishes a supported verification integration path.

## Architecture

The repository remains the specification and deterministic factory. Canonical checked-in state is limited to manifests, source pins, schemas, code, tests, and small fixture data. Large acquired source payloads live under `.cache/` and generated Hugging Face artifacts live under `build/` unless explicitly released elsewhere.

Pipeline:

```text
collection manifest + inventory
             |
             v
     validate collection
             |
             v
     acquire pinned sources
       |             |
       |             +--> ZLBB puzzle endpoint -> hash/cache
       +----------------> pinned om-leaderboard checkout
             |
             v
      ingest observations
             |
             v
     verify with libverify
             |
             v
 canonical JSONL manifests
             |
             v
  Hugging Face Parquet export
             |
             v
      release validation
```

## Task 3: Acquire and index leaderboard records

Files:

- `opus_corpus/acquire.py`
- `opus_corpus/leaderboard.py`
- `tests/fixtures/leaderboard/...` (tiny text fixtures only; no third-party binary payloads committed)
- `tests/test_leaderboard.py`

Behavior:

- `python -m opus_corpus fetch leaderboard --cache .cache` clones/fetches the exact pinned `om-leaderboard` commit into a content-addressed source directory.
- Ingestion walks only directories mapped from the frozen collection inventory.
- Every `.json` record must resolve its `dataPath` to a sibling/in-repository `.solution` artifact.
- Read score metadata, source author/submission metadata when present, source path, and solution bytes.
- Compute SHA-256 and byte length for every solution.
- Construct immutable source URLs using the pinned commit.
- Exact-byte duplicates become one solution artifact with multiple observations.
- Preserve every source record observation even when its score metadata is identical to another record.
- Reject path traversal, missing solution files, malformed JSON, and out-of-collection puzzle directories.

TDD sequence:

1. Add tiny synthetic repository fixtures and failing ingestion tests.
2. Implement deterministic record discovery and hashing.
3. Validate deduplication/provenance behavior.
4. Run full suite.

Acceptance:

- fixture ingestion is order-independent and deterministic;
- no mutable branch URL enters canonical output;
- raw bytes remain in the local cache, not generated publication files.

## Task 5: Integrate `omsim/libverify`

Files:

- `opus_corpus/verify.py`
- `tests/test_verify.py`
- `.cache/tools/omsim/...` at runtime only

Behavior:

- Fetch/build exactly `ianh/omsim@758f4a4b4c9e24f50294801da774a0960c922bab`.
- Build `libverify.so` with the upstream Makefile.
- Use `ctypes` to call the public verifier API.
- For every solution artifact, pair it with the puzzle named inside the solution bytes and require that identity to resolve to the expected canonical puzzle.
- Compute at minimum `cost`, `cycles`, `area`, and `instructions`.
- Also retain deterministic leaderboard-compatible metrics exposed by the pinned verifier when available: overlap, trackless, width, height, bounding hex, rate, and steady-state/infinity metrics.
- Compare verifier-computed values to source-declared leaderboard score fields without overwriting either.
- Store structured parse/simulation/metric errors rather than dropping candidates.

TDD sequence:

1. Unit-test metric normalization/error handling behind a small verifier interface using a fake implementation.
2. Implement ctypes adapter only after the interface tests fail as expected.
3. Add an integration test gated on `OMSIM_LIBVERIFY` or an available built library.
4. GitHub Actions builds real `libverify.so` and runs the integration test against a small hydrated fixture selected from the pinned leaderboard source.

Acceptance:

- verification result identity includes verifier revision and validation-profile version;
- source claims and verifier measurements are both preserved;
- at least one verified solution exists for every collection puzzle in a live build, otherwise release validation fails.

- `verifications.jsonl`

Rules:

- Rows are sorted by stable IDs/hashes, never filesystem discovery order.
- Solution identity is SHA-256 of exact bytes for v1.
- Observation identity is deterministic from source ID + source revision + source path/object key.
- Verification identity is deterministic from puzzle artifact hash + solution hash + verifier revision + validation-profile version.
- Manifest records source pins, counts, coverage, output hashes, build software revision when available, and validation-profile version.
- Canonical JSON serialization uses UTF-8, sorted keys, stable separators, and newline termination.

- pinned source URL;
- source author/submitter fields where present;
- source-claimed metrics;
- verifier-computed metrics/status;
- provenance linkage;
- rights status.

They do not contain raw `.solution` or `.puzzle` bytes by default.
